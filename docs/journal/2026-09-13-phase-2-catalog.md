**FIND-14 · Официальная коллекция Braze выгружается скриптом без токена — через documenter API**
`RISK-1` считал источник неподтверждённым. Замер 13.09 (сегодня) показывает обратное.

Рабочий адрес — тот самый, на который ссылается собственная документация Braze
(https://www.braze.com/docs/api/postman_collection):

    https://documenter.getpostman.com/api/collections/4689407/SVYrsdsG

Проверено curl'ом: HTTP 200, 565 438 байт, JSON коллекции (schema v2.0.0, `info.name` =
"Braze Endpoints"). Токен не нужен.

Что в ней: 99 запросов, 32 папки, 10 папок верхнего уровня. Методы —
GET 44, POST 45, PUT 4, DELETE 4, PATCH 2. Присутствуют все эндпоинты, которые уже
подтверждены живыми ответами по `NEED-11`, и `/users/export/ids` (случай `FIND-13`).

Три последовательные загрузки дали побайтово одинаковый файл (sha256 совпал), значит
`spec:sync` даст осмысленный git-диф, а не шум при каждом запуске — это ровно то, ради
чего §7 требований просит коммитить снимок.

Чего НЕ работает и почему это неважно: `https://api.getpostman.com/collections/<uid>`
отдаёт 401 «Invalid API Key» — это официальное Postman API, ему нужен токен. Оно не нужно:
documenter отдаёт ту же коллекцию анонимно.

**FIND-15 · В коллекции 4 пары запросов с одинаковым METHOD+путь — запасной идентификатор из §9 на них схлопнется**
Замер по загруженной коллекции (см. FIND-14): 99 запросов, но различных `METHOD + путь`
только 95. Идентификаторы Postman при этом уникальны — все 99.

Совпадают, все четыре пары — папка «Subscription Groups», подпапки Email и
SMS and WhatsApp, один и тот же эндпоинт задокументирован дважды с разными примерами:

    GET  /subscription/status/get      488c8923… / 4b8515b8…
    GET  /subscription/user/status     d1c3b617… / 54bd7ca8…
    POST /v2/subscription/status/set   b1b9a0e0… / 81a5fe65…
    POST /subscription/status/set      8895e87e… / 72558b32…

Почему важно для `CAT-3`: §9 требований говорит «предпочитать id запроса Postman, запасной
вариант — METHOD + нормализованный путь». Здесь видно, что запасной вариант схлопывает
четыре операции молча — ровно то, что §12 запрещает. Postman-id есть у всех 99 запросов,
так что развилка на практике не наступает; но тест на схлопывание идентификаторов написать
надо, иначе это вскроется на следующей выгрузке.

Отдельный вопрос — как эти две пары назвать командами, раз путь один. Это `CAT-4`
(оверрайды), не `CAT-3`.

**RISK-2 · Адрес выгрузки коллекции — внутреннее API Postman, оно может измениться без предупреждения**
`https://documenter.getpostman.com/api/collections/4689407/SVYrsdsG` (FIND-14) — это то, чем
питается страница документации, на которую ссылается Braze. Postman нигде не описывает этот
адрес как публичный интерфейс, и обещаний по нему не даёт.

Чем это НЕ является: угрозой работоспособности CLI. Снимок коллекции закоммичен и именно он
уезжает с пакетом (§6–§7 требований). Если адрес умрёт, сломается только `spec:sync` —
шаг разработчика, — а собранный CLI продолжит работать на последнем снимке. Это ровно та
развязка, ради которой архитектура и требует коммитить снимок.

Что делать: `spec:sync` обязан отличать «Braze поменял коллекцию» от «адрес перестал
отвечать» и падать с разными сообщениями. Тихо перезаписать снимок пустотой или HTML-кой —
единственный сценарий, при котором эта штука по-настоящему кусается. Проверка формата
(это JSON, в нём есть `info.schema` и непустой `item`) до записи в `spec/`.

Запасной путь, если адрес отвалится: ручной экспорт из Postman (строка 2 таблицы в плане) —
владелец экспортирует коллекцию один раз, `spec:sync` переходит из «скачать» в «проверить и
записать». Форма снимка от этого не меняется, поэтому переключение не переписывает ни
нормализатор, ни оверрайды.
