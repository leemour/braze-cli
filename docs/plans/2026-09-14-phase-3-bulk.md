# Plan: Phase 3 — the bulk pipeline

**Done means:** `braze production users track --records users.jsonl` sends 750 000 user updates to
Braze in bounded memory, leaves one audit row per user — not per HTTP request — and can be
interrupted with Ctrl+C without corrupting that audit or lying about what reached Braze.

Written 2026-09-14 against `11c9393`, with Phase 2 complete, `CORE-10` closed and 381 tests green.
Backlog items `BULK-1`…`BULK-10` plus `CLI-13` in [`../../BACKLOG.md`](../../BACKLOG.md); brief in
[`../REQUIREMENTS.md`](../REQUIREMENTS.md) §24, §25, §33–§40, §53.

---

## 1. The thing that decides the rest

**The audit file is the product, not the HTTP calls.** Everything else here — streaming, batching,
backpressure — exists so that at the end of a 750 000-record run somebody can answer *"what
happened to row 481 927?"* without having been watching.

That forces three things which are otherwise easy to get wrong, and each has already been decided
in this repository's rules:

- **One HTTP request carrying 75 users is 75 audit rows** (rule 5). A batch is a transport detail;
  the user is the unit anyone cares about.
- **Their status is `submitted`, never `success`** — Braze does not acknowledge them one by one, so
  claiming it did would be a lie the audit exists to prevent.
- **A connection that died after the request left is `unknown`, never `failed`** (rule 4, §24).
  Braze may well have processed it. Reporting `failed` invites a re-run that double-applies.

## 3. Decisions

### 3.1 The executor is portable; everything that touches a file is not

The brief's §53 puts `bulk` under `core/src/`. That holds, with a hard line through it:

| Lives in `packages/core` | Lives in `packages/cli` |
|---|---|
| the executor: `AsyncIterable<BulkRecord>` in, `AsyncIterable<BulkOutcome>` out | the parsers — JSONL, CSV, JSON from a file or stdin |
| batching to `batchTotal`, the bounded queue, concurrency | `records.csv`, written as outcomes arrive |
| deciding each record's truthful status | the progress UI, and the signal handler |

Core never learns what a file is. **The executor takes an async iterable and returns one**, so the
same code runs against a database cursor, a generator, or another program's output — §37 asks for
exactly that, and it is also what makes a million-record test possible without a million requests.

### 3.2 A record is not a row, and the operation says how it batches

`batch` already names the body fields that hold arrays and `batchTotal` caps them together. So:

**Corrected 2026-09-15, when step 3 was built.** The version below said `recordId: string` on the
input record. It is optional there and mandatory on the **outcome** — `packages/core/src/bulk/types.ts:13`.
Nothing in the request body uses it, so it is purely an audit field, and putting the "never blank"
rule in the executor means one runtime place enforces it instead of three parsers and every §37
caller with a database cursor each remembering to. The executor therefore takes a **required
`runId`**: a default prefix would silently make two runs' generated ids collide, which is exactly
the ambiguity a bare row number was rejected for.

```ts
interface BulkRecord {
  /** Source position, 1-based. */
  row: number
  /** The input's own id, where it carried one. Absent or blank means the executor generates it. */
  recordId?: string
  /** Which `batch` field this belongs in — `attributes`, `events`, `purchases`. */
  field: string
  value: unknown
  /**
   * Braze's own identifiers, copied out for the audit — derived from `value` when the producer
   * supplies none. **Nothing is discarded from `value`** — that goes to Braze intact, or we would
   * be sending empty user objects. §35 constrains what the CSV keeps, not what is sent.
   */
  identity?: BrazeIdentifiers
}

interface BulkOutcome {
  row: number
  /**
   * **Mandatory, and ours** (`NEED-31`). The input's id where it had one, `<runId>-<row>` where it
   * did not. Never blank: an audit row nobody can act on is not an audit. A blank string from a CSV
   * column counts as "did not".
   */
  recordId: string
  /** Whether `recordId` came from the data or from us. A generated id must never look customer-owned. */
  recordIdSource: "input" | "generated"
  // …status, batchId, identity, and what Braze said
}
```

**Why not the bare row number, which `NEED-31` names as the floor.** Row 5 of which file, from
which run? `<runId>-<row>` is unique across every run this tool has ever made and points at both
the run directory and the input line. It costs nothing and it is the difference between an audit
that can be acted on a week later and one that cannot.

The executor fills one request from consecutive records until `batchTotal` is reached, grouping by
`field` **within** the batch rather than across it, so order is preserved and a row's position
never depends on how far ahead the batcher looked.

**Records whose `field` is not in the operation's `batch` are `invalid`, not an error.** One bad
line in two million must not end the run — §34 lists `invalid` as a status precisely for this.

### 3.3 Every record is checked before it joins a batch

`NEED-31`, second half: *"we do not send whatever turns up"*. This goes further than `CORE-10`,
and the difference matters in exactly one way — **one malformed record among 75 would fail the
whole batch**. So validation moves from the assembled body to the individual record.

| | `CORE-10` today | here |
|---|---|---|
| what is checked | the whole request body | each record on its own |
| when | once, before the request | before the record joins a batch |
| a failure means | the request is refused | that record is `invalid`; the other 74 still go |

`schemas.ts` gains **per-record schemas**, keyed by operation and `field`, beside the body schemas
it already holds. Braze states the requirement for `/users/track` directly: *"For each request
component … you must include one of `external_id`, `user_alias`, `braze_id`, `email`, or `phone`"*
— so a record carrying none of them cannot work and there is no reason to spend a request finding
out. Each per-record schema is read from Braze's own page before it is written, under `CORE-10`'s
rule: **an ambiguous page means no schema**, and the records pass unchecked rather than wrongly
refused.

The invalid record still gets an audit row, with `status: invalid` and the reason. It is not an
error and does not end the run — one bad line in two million must not.

### 3.4 Backpressure is pull-based, and the parser is never ahead

§39 forbids the parser enqueuing two million promises. The executor therefore **pulls**:

```
while queue.size + queue.pending < concurrency * 2:
    pull the next batchTotal records from the iterable
    enqueue one request
```

The iterable is only advanced when there is room, so the parser reads at the speed Braze accepts
work. Nothing buffers except the batch being filled and the queue's small window.

Default concurrency 4 (§38), queue bounded at `concurrency * 2`. **The number that matters for
memory is the product**: at most `concurrency * 2 * batchTotal` records are resident at once —
4 × 2 × 75 = **600 records**, whatever the input size. That is the ceiling `bulk-memory.test.ts`
asserts against, rather than a general hope that streaming keeps things small.

### 3.5 Status is decided per record, from what Braze actually said

| What happened | Status |
|---|---|
| `--dry-run` | `planned` |
| the batch got a 2xx | `submitted` — never `success`, no per-user acknowledgement exists |
| the batch got a 2xx, and `errors` names this record's index | `failed` — Braze rejected this object and created nothing |
| the batch got a 2xx, and `errors` holds an entry we cannot place | `unknown` for the records that entry might be |
| the batch got a 4xx | `failed` |
| transport died after the request left | `unknown` (§24, rule 4) |
| the record did not fit the operation | `invalid` |
| the run was interrupted before this record was sent | `skipped` |

**`RISK-3` is measured, 2026-09-15 — and the answer is the good one.** The two rows above replace
what this section said before: that Braze documents no attribution, so an `errors` array made the
**whole batch** `unknown`. It does attribute, the docs simply do not say so. One `/users/track`
batch to the staging workspace — five objects, three sound and two broken in different documented
ways — came back `201`, `"message": "success"`, and:

```json
{"attributes_processed": 2,
 "errors": [
   {"index": 1, "input_array": "attributes", "type": "'email_subscribe' must be 'subscribed', 'unsubscribed', or 'opted_in'"},
   {"index": 3, "input_array": "attributes", "type": "'push_subscribe' must be 'subscribed', 'unsubscribed', or 'opted_in'"},
   {"index": 4, "input_array": "attributes", "type": "You must specify only one of 'external_id', 'user_alias' or 'braze_id'"}]}
```

Three things follow, and step 4 is built on them:

- **`index` is 0-based and counted inside `input_array`, not across the request.** So a record's
  position in *its own field's array* is what has to be recorded at dispatch — which is exactly
  what grouping the batch by field already produces.
- **`attributes_processed` cross-checks the attribution.** Processed plus errors equals objects
  sent (2 + 3 = 5). When that sum does not hold, some rejection is unexplained, and *then* the
  unexplained remainder is `unknown`. The fallback survives as the rare case, not the rule.
- **A rejected object creates nothing.** Checked with `/users/export/ids`: the two processed
  profiles exist and the three rejected ones do not. So `failed` is the truthful status for them —
  there is no partial write to be uncertain about.

**Parse it leniently.** The page documents the error codes but never the shape — neither "index"
nor "input_array" appears on it, and the example renders as `[ { <error message> } ]`. This is
knowledge from one measurement, so a missing `index`, an unknown `input_array` or a count that does
not add up degrades to `unknown` rather than throwing. What must never depend on it is sending.

This is why `ExecuteResult.raw` has existed since Phase 1: a pipeline reading only the status code
would mark 75 users `submitted` and never look at what Braze actually said.

### 3.6 The audit is written as work completes, not at the end

`records.csv` is appended row by row as outcomes arrive, so a run killed at record 1 800 000 still
has 1 800 000 rows. Columns per §33, plus `record_id` and `record_id_source` from `3.2` — **there
is no such thing as a row without an identifier** (`NEED-31`).

**The CSV keeps identifiers only** — never arbitrary attributes (§35). The parser copies
`external_id`, `braze_id` and the user alias pair into `identity` for the audit; **`value` travels
to Braze unchanged**. Reducing the record before dispatch would send Braze empty user objects,
which is the obvious misreading of §35 and worth stating so nobody implements it.

### 3.7 The summary is the result of a bulk run

A single request prints Braze's response. **A bulk run has no single response**, so the thing the
caller actually asked for — what became of 750 000 records — is the summary. It goes through
`renderer.result`, which means stdout in both modes: one JSON object for an agent, a table for a
person. Not a diagnostic; it is the answer.

```
750 000 records · 10 000 batches · 4 concurrent · 6m 12s · 2 016 records/sec

  submitted   749 203   sent in a batch Braze accepted
  failed          612   Braze refused them
  invalid         185   refused here, before sending — see records.csv for why
  unknown           0   may have been applied; the connection died after sending
  skipped           0   never sent — the run was interrupted

  10 014 HTTP requests · 14 retries · records.csv has a row for every one of the 750 000
```

**`submitted` is the word, and the summary says what it means.** Braze does not acknowledge
individual users, so the count of things that definitely worked is a number this tool cannot
produce — and printing "successful: 749 203" would be exactly the lie §1 exists to prevent. The
gloss beside each number is there because a reader who sees only the word will assume the stronger
meaning.

**`invalid` and `failed` are separate on purpose**, which is the distinction the owner asked for:
`invalid` never cost a request and is entirely our judgment; `failed` is Braze's. A run with 185
invalid and 0 failed means the input is wrong. A run with 0 invalid and 612 failed means our
validation is too loose and those 612 should have been caught here.

`RunMetadata` in `packages/cli/src/runs/run.ts:16` reserves `inputRecords`, `submittedRecords`,
`failedRecords` and `unknownRecords` — **four of the six statuses §34 lists.** It gains
`invalidRecords` and `skippedRecords`, and `run.json` and the printed summary are generated from
one count each, never tallied twice.

### 3.8 Ctrl+C is a phase of the run, not a crash

`CLI-13` first, because `BULK-8` is unimplementable without it. On `SIGINT`/`SIGTERM`: stop pulling
the iterable → stop scheduling → let in-flight requests finish (they may already have reached
Braze) → mark everything unsent `skipped` → flush the CSV → finalize `run.json` with
`status: "cancelled"` → exit. A second signal exits immediately and says what it abandoned.

`run.finish` is already idempotent and called on every path, so this is wiring a handler to
machinery that exists.

### 3.9 `--records` is a new flag, not a new meaning for `--input` — ruled `NEED-30`

`--input @file.json` sends the file as **one** body and must keep doing so — it is what every
write in the CLI uses today. `--records <source>` means "this file holds many records; batch them".
Two flags, because the difference is not a detail: one sends a request, the other sends ten
thousand. Passing both is an error.

**Ruled by the owner 2026-09-15 (`NEED-30`, option A).** The alternative — a separate `braze bulk users track`
verb — was rejected because it would put every one of the 95 generated operations into the surface
twice, `braze commands --json` and `docs/commands.md` included.

## 4. Order of work

Each step ends green and is committable alone.

### Step 1 — `CLI-13`, the signal handler — ✅ done 2026-09-15
A run owns an `AbortController`; `run.signal` reaches `client.execute`, which has accepted one
since Phase 1 and was never given it. The handler cancels, awaits the idempotent `run.finish`,
exits 130; a second signal exits at once.

**Cancellation is decided from the signal, not the error code.** The handler and `runOperation`'s
catch both call `finish`, and whichever won would otherwise decide the status — a Ctrl+C recorded
as `failed` with whatever the dying connection reported. `outcome_unknown` survives it: a write
that may have reached Braze is not made safe by our having stopped waiting (rule 4).

**Checked end to end on 2026-09-15** (`FIND-26`), which replaces this section's warning that it
never had been. A real `SIGINT` to a confirmed pid gave exit 130, the handler's message, a complete
`run.json` carrying `"status": "cancelled"`, and an `events.jsonl` with no truncated line.

Two things made it work where three earlier attempts signalled the wrong process (`FIND-22`):
`( echo $BASHPID > pidfile; exec node … ) &` puts the pid of the process itself in the file, and
the pid is confirmed by **full command line** — `ps -o comm=` prints `MainThread` for node, not
`node`. The hang came from a throwaway profile pointing at `https://192.0.2.1`, so no request ever
left for Braze.

It remains a manual check with nothing in CI: a test spawning `dist/` would be red, because CI runs
`pnpm test` before `pnpm build`. **Step 6 is where it becomes automatic**, against `records.csv`
and its tail of `skipped` rows.

### Step 2 — `BULK-1` `BULK-3` `BULK-4`, the executor — ✅ done 2026-09-15
`packages/core/src/bulk/`. 400 tests. No files, no CSV, no CLI — driven entirely by hand-built
async iterables.

**`BUG-9`, caught by the backpressure test rather than by eye.** The bound was on the queue:
`queue.size + queue.pending < concurrency * 2`. That looks right and is not — when Braze answers
faster than the consumer reads, the queue empties *between* pulls and the loop reads the whole
input into an unbounded buffer. Measured: 100 000 records pulled for a consumer that had taken
one, so §39 was being broken by the code meant to enforce it.

The fix is one term. `ready.length` — work finished but not yet yielded — joins the bound, so what
is limited is **all outstanding work**. The invariant `3.4` promised is now true: at most
`concurrency * 2 * batchSize` records resident, 600 at the defaults, whatever the input size.

A second, smaller one: `yield` suspends the generator, and a batch completing mid-yield woke
nothing, leaving the next wait asleep forever. A progress flag closes it.

### Step 3 — `NEED-31`, identity and per-record validation — ✅ done 2026-09-15
Every outcome gets a `recordId` — from the input, or generated — and `recordSchemas` went into
`packages/core/src/operations/schemas.ts:89`, each read from Braze's page first. 423 tests.

**Braze's identifier rule has an exception, and missing it would have broken a documented import.**
The attributes page requires one of the five identifiers per object *and* says an anonymous push
token import carries none: "you can import the legacy tokens for anonymous users without providing
`external_id` by specifying `push_token_import` as `true`". A schema written from the first sentence
alone refuses that import outright, with no recourse but `braze api`.

**The primary-identifier rule is the catch that pays for the step.** "Only one primary identifier is
allowed per request object—including more than one causes that object to be rejected" — and Braze
rejects it *inside a 2xx*, so without this check the record costs a request and comes back a
`failed` audit row instead of an `invalid` one that names the reason before sending. The
measurement in `3.5` produced exactly that rejection: "You must specify only one of 'external_id',
'user_alias' or 'braze_id'".

**A batch's budget is records read, not records sent.** A refused record still counts against
`batchSize`, so a file where every line is malformed cannot grow one unit without bound. The price
is a short request when a batch contains bad lines — paid only by input that is already wrong.

### Step 4 — `BULK-6`, truthful status — ✅ done 2026-09-15
The table in `3.5`, built on the measurement that opens it. `packages/core/src/bulk/verdict.ts`
holds it as a pure function — placements in, a verdict per row out — so the response Braze really
sent is replayed as a fixture instead of re-enacted over HTTP. 440 tests.

**The count check notes rather than condemns.** `attributes_processed` is documented as what Braze
*queued*, and the identity "queued + refused = sent" rests on a single measurement. Making it
load-bearing would let a benign mismatch turn a whole run of truthful rows into `unknown` ones —
an audit nobody can scope a re-run from. So a mismatch leaves the records `submitted` and puts the
arithmetic in a `note` on the row. `unknown` keeps to the two cases with direct evidence: an error
we could not place, and a connection that died after sending.

**No `errorCode` on a record Braze refused inside a 2xx.** The closed list describes a request that
failed, and that request succeeded. Braze's own sentence is the only taxonomy that exists for one
refused object, and it travels in `errorMessage`.

### Step 5 — `BULK-2`, the parsers
JSONL, CSV, JSON. Streaming, in the CLI. JSONL first — it is the format §28 prefers and the only
one that is trivially streamable; CSV second; JSON array last, and only if it can be streamed
rather than parsed whole.

### Step 6 — `BULK-5` `BULK-7` `BULK-8` `BULK-12`, the artifacts and the interface

## 6. What will bite

- **`batchTotal`, not `batch`.** `BUG-8`: Braze caps `/users/track` at 75 objects across the three
  arrays together, and the per-field 75 is their legacy limit. Batching by `batch` sends 225 and
  has every request refused. A test pins this directly.
- **A write is never retried automatically** (rule 4). The queue must not quietly retry a failed
  batch; `mayRetry` already answers this per operation and the executor must ask it.
- **`--dry-run` must produce a full `records.csv` of `planned` rows.** That is how somebody checks
  a 2-million-row file before spending real requests, and it is the main reason to run this at all
  the first time.
- **Progress output is stderr, pretty mode only.** Rule 3 has a test; a progress bar on stdout
  would break every agent reading JSON.
- **Never send a non-GET to production without asking** (rule 13). This entire phase is writes, so
  the rule applies to all of it and needs no new flag to say so: every live check goes to the
  sandbox, and the million-record test never leaves the process. The `--confirm` that guards
  updating one user guards updating 750 000 the same way.

## 7. What was ruled, and what is still unknown

**All three owner questions are answered** and are rulings in [`../DECISIONS.md`](../DECISIONS.md):

- **`NEED-30` — option A.** A `--records` flag on the existing command; no `braze bulk` verb. A
  second command tree would put every one of the 95 generated operations into the surface twice,
  `braze commands --json` and `docs/commands.md` included.
- **`NEED-31` — neither option offered; the question was too narrow.** Not "what goes in the blank
  cell" but "there are no blank cells": every record carries an identifier, it is ours, and
  required fields are checked before the request rather than after Braze refuses it. `3.2` and
  `3.3` are written from that ruling.
- **`NEED-32` — option A.** A completed run exits 0 however many records failed. The summary on
  stdout is what a script branches on, because an exit code cannot carry "612 of 750 000, and here
  is which". Non-zero on any failure was rejected for making one bad row in a two-million-row file
  look like a wrong API key; the existing mapping still covers everything that genuinely raises.

**`RISK-3` is closed, 2026-09-15.** How Braze attributes an error inside a 2xx was a measurement,
and it was taken: `index` plus `input_array` per error entry, cross-checked by
`attributes_processed`. The answer and what it changes are in `3.5`; the raw response is in the
journal under `FIND-25`.

Nothing is waiting on the owner.

## 8. Out of scope

`braze run resume <run-id>` (`BULK-11`, Phase 4) — but the audit format must already make
"submitted / failed / unknown / not started" answerable per source record, or resume becomes
impossible later. Worker threads: §38 rules them out for HTTP concurrency.
