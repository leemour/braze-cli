# Plan: Phase 3 — the bulk pipeline

**Done means:** `braze production users track --records users.jsonl` sends 750 000 user updates to
Braze in bounded memory, leaves one audit row per user — not per HTTP request — and can be
interrupted with Ctrl+C without corrupting that audit or lying about what reached Braze.

Written 2026-09-14 against `11c9393`, with Phase 2 complete, `CORE-10` closed and 381 tests green.
Backlog items `BULK-1`…`BULK-10` plus `CLI-13` in [`../../BACKLOG.md`](../../BACKLOG.md); brief in
[`../REQUIREMENTS.md`](../REQUIREMENTS.md) §24, §25, §33–§40, §53.

---

## 1. The thing that decides the rest

**The audit file is the product, not the HTTP calls.** Everything else here — streaming, batching,
backpressure — exists so that at the end of a 750 000-record run somebody can answer *"what
happened to row 481 927?"* without having been watching.

That forces three things which are otherwise easy to get wrong, and each has already been decided
in this repository's rules:

- **One HTTP request carrying 75 users is 75 audit rows** (rule 5). A batch is a transport detail;
  the user is the unit anyone cares about.
- **Their status is `submitted`, never `success`** — Braze does not acknowledge them one by one, so
  claiming it did would be a lie the audit exists to prevent.
- **A connection that died after the request left is `unknown`, never `failed`** (rule 4, §24).
  Braze may well have processed it. Reporting `failed` invites a re-run that double-applies.

## 3. Decisions

### 3.1 The executor is portable; everything that touches a file is not

The brief's §53 puts `bulk` under `core/src/`. That holds, with a hard line through it:

| Lives in `packages/core` | Lives in `packages/cli` |
|---|---|
| the executor: `AsyncIterable<BulkRecord>` in, `AsyncIterable<BulkOutcome>` out | the parsers — JSONL, CSV, JSON from a file or stdin |
| batching to `batchTotal`, the bounded queue, concurrency | `records.csv`, written as outcomes arrive |
| deciding each record's truthful status | the progress UI, and the signal handler |

Core never learns what a file is. **The executor takes an async iterable and returns one**, so the
same code runs against a database cursor, a generator, or another program's output — §37 asks for
exactly that, and it is also what makes a million-record test possible without a million requests.

### 3.2 A record is not a row, and the operation says how it batches

`batch` already names the body fields that hold arrays and `batchTotal` caps them together. So:

```ts
interface BulkRecord {
  /** Source position, 1-based. */
  row: number
  /**
   * **Mandatory, and ours** (`NEED-31`). Taken from the input where it supplies one, generated as
   * `<runId>-<row>` where it does not. Never blank: an audit row nobody can act on is not an audit.
   */
  recordId: string
  /** Whether `recordId` came from the data or from us. A generated id must never look customer-owned. */
  recordIdSource: "input" | "generated"
  /** Which `batch` field this belongs in — `attributes`, `events`, `purchases`. */
  field: string
  value: unknown
  /**
   * Braze's own identifiers, copied out for the audit. **Nothing is discarded from `value`** —
   * that goes to Braze intact, or we would be sending empty user objects. §35 constrains what the
   * CSV keeps, not what is sent.
   */
  identity?: BrazeIdentifiers
}
```

**Why not the bare row number, which `NEED-31` names as the floor.** Row 5 of which file, from
which run? `<runId>-<row>` is unique across every run this tool has ever made and points at both
the run directory and the input line. It costs nothing and it is the difference between an audit
that can be acted on a week later and one that cannot.

The executor fills one request from consecutive records until `batchTotal` is reached, grouping by
`field` **within** the batch rather than across it, so order is preserved and a row's position
never depends on how far ahead the batcher looked.

**Records whose `field` is not in the operation's `batch` are `invalid`, not an error.** One bad
line in two million must not end the run — §34 lists `invalid` as a status precisely for this.

### 3.3 Every record is checked before it joins a batch

`NEED-31`, second half: *"we do not send whatever turns up"*. This goes further than `CORE-10`,
and the difference matters in exactly one way — **one malformed record among 75 would fail the
whole batch**. So validation moves from the assembled body to the individual record.

| | `CORE-10` today | here |
|---|---|---|
| what is checked | the whole request body | each record on its own |
| when | once, before the request | before the record joins a batch |
| a failure means | the request is refused | that record is `invalid`; the other 74 still go |

`schemas.ts` gains **per-record schemas**, keyed by operation and `field`, beside the body schemas
it already holds. Braze states the requirement for `/users/track` directly: *"For each request
component … you must include one of `external_id`, `user_alias`, `braze_id`, `email`, or `phone`"*
— so a record carrying none of them cannot work and there is no reason to spend a request finding
out. Each per-record schema is read from Braze's own page before it is written, under `CORE-10`'s
rule: **an ambiguous page means no schema**, and the records pass unchecked rather than wrongly
refused.

The invalid record still gets an audit row, with `status: invalid` and the reason. It is not an
error and does not end the run — one bad line in two million must not.

### 3.4 Backpressure is pull-based, and the parser is never ahead

§39 forbids the parser enqueuing two million promises. The executor therefore **pulls**:

```
while queue.size + queue.pending < concurrency * 2:
    pull the next batchTotal records from the iterable
    enqueue one request
```

The iterable is only advanced when there is room, so the parser reads at the speed Braze accepts
work. Nothing buffers except the batch being filled and the queue's small window.

Default concurrency 4 (§38), queue bounded at `concurrency * 2`. **The number that matters for
memory is the product**: at most `concurrency * 2 * batchTotal` records are resident at once —
4 × 2 × 75 = **600 records**, whatever the input size. That is the ceiling `bulk-memory.test.ts`
asserts against, rather than a general hope that streaming keeps things small.

### 3.5 Status is decided per record, from what Braze actually said

| What happened | Status |
|---|---|
| `--dry-run` | `planned` |
| the batch got a 2xx | `submitted` — never `success`, no per-user acknowledgement exists |
| the batch got a 2xx **with a populated `errors` array** | see `RISK-3` immediately below |
| the batch got a 4xx | `failed` |
| transport died after the request left | `unknown` (§24, rule 4) |
| the record did not fit the operation | `invalid` |
| the run was interrupted before this record was sent | `skipped` |

⚠ **`RISK-3`: Braze does not document how an entry in `errors` maps back to an input object.**
Their page lists the error codes (`BAD_DEVICE_ID`, `EMAIL_BAD_FORMAT`, …) and says data unaffected
by an error is still processed — but says nothing about an index, an array name or an identifier
tying the error to one of the 75 objects that were sent. This is the load-bearing claim of the
whole status design and it is currently **unverified**.

Both obvious readings are lies:

- marking all 75 `submitted` says everything landed, when Braze just said some did not;
- marking all 75 `failed` invites a re-run that double-applies whatever *did* land.

**So an unattributable error makes the whole batch `unknown`**, carrying Braze's message. That is
what `unknown` means (§34) and it is the honest answer. It is worse for reporting, which is the
point: the audit's job is to be true, not tidy.

**Step 4 begins by settling this empirically** — one batch of three objects to the sandbox, one of
them deliberately malformed, and read what comes back. Rule 13 restricts non-GET to *production*;
the sandbox is where this belongs. If Braze does attribute the error, the table gains the
`failed`-per-record row and `BulkRecord` gains the index recorded at dispatch. Until then the
`unknown` fallback is the specified behaviour, not a placeholder.

This is why `ExecuteResult.raw` has existed since Phase 1: a pipeline reading only the status code
would mark 75 users `submitted` and never look at what Braze actually said.

### 3.6 The audit is written as work completes, not at the end

`records.csv` is appended row by row as outcomes arrive, so a run killed at record 1 800 000 still
has 1 800 000 rows. Columns per §33, plus `record_id` and `record_id_source` from `3.2` — **there
is no such thing as a row without an identifier** (`NEED-31`).

**The CSV keeps identifiers only** — never arbitrary attributes (§35). The parser copies
`external_id`, `braze_id` and the user alias pair into `identity` for the audit; **`value` travels
to Braze unchanged**. Reducing the record before dispatch would send Braze empty user objects,
which is the obvious misreading of §35 and worth stating so nobody implements it.

### 3.7 Ctrl+C is a phase of the run, not a crash

`CLI-13` first, because `BULK-8` is unimplementable without it. On `SIGINT`/`SIGTERM`: stop pulling
the iterable → stop scheduling → let in-flight requests finish (they may already have reached
Braze) → mark everything unsent `skipped` → flush the CSV → finalize `run.json` with
`status: "cancelled"` → exit. A second signal exits immediately and says what it abandoned.

`run.finish` is already idempotent and called on every path, so this is wiring a handler to
machinery that exists.

### 3.8 `--records` is a new flag, not a new meaning for `--input` — ruled `NEED-30`

`--input @file.json` sends the file as **one** body and must keep doing so — it is what every
write in the CLI uses today. `--records <source>` means "this file holds many records; batch them".
Two flags, because the difference is not a detail: one sends a request, the other sends ten
thousand. Passing both is an error.

**Ruled by the owner 2026-09-15 (`NEED-30`, option A).** The alternative — a separate `braze bulk users track`
verb — was rejected because it would put every one of the 95 generated operations into the surface
twice, `braze commands --json` and `docs/commands.md` included.

## 4. Order of work

Each step ends green and is committable alone.

### Step 1 — `CLI-13`, the signal handler
Not bulk, but `BULK-8` needs it and it is small: a handler that calls the existing idempotent
`run.finish`. Proves itself on a single-request command before anything streams.

### Step 2 — `BULK-1` `BULK-3` `BULK-4`, the executor
The core of it, driven entirely by hand-built async iterables in tests. Batching to `batchTotal`,
the bounded queue, backpressure. **No files, no CSV, no CLI.** Ends with a test that a slow
consumer never lets the producer run ahead.

### Step 3 — `NEED-31`, identity and per-record validation
Every record gets a `recordId` — from the input, or generated — and per-record schemas go into
`schemas.ts`, each read from Braze's page first. **Before the status work**, because a record
refused here never reaches Braze and so never needs a status from Braze.

### Step 4 — `BULK-6`, truthful status
The table in `3.5`, including parsing Braze's `errors` array out of a 2xx. Deserves its own step
because it is the part that can quietly lie.

### Step 5 — `BULK-2`, the parsers
JSONL, CSV, JSON. Streaming, in the CLI. JSONL first — it is the format §28 prefers and the only
one that is trivially streamable; CSV second; JSON array last, and only if it can be streamed
rather than parsed whole.

### Step 6 — `BULK-5` `BULK-7` `BULK-8`, the artifacts and the interface
`records.csv` streamed as outcomes arrive, the progress UI (pretty mode only — rule 3), and the
signal handling wired to the executor.

### Step 7 — `BULK-9`, the million-record proof
A synthetic run against the mock, asserting heap stays flat. The test that makes all of the above
more than an intention.

`BULK-10` (`braze runs cleanup`) is P3 and out of this sequence.

## 6. What will bite

- **`batchTotal`, not `batch`.** `BUG-8`: Braze caps `/users/track` at 75 objects across the three
  arrays together, and the per-field 75 is their legacy limit. Batching by `batch` sends 225 and
  has every request refused. A test pins this directly.
- **A write is never retried automatically** (rule 4). The queue must not quietly retry a failed
  batch; `mayRetry` already answers this per operation and the executor must ask it.
- **`--dry-run` must produce a full `records.csv` of `planned` rows.** That is how somebody checks
  a 2-million-row file before spending real requests, and it is the main reason to run this at all
  the first time.
- **Progress output is stderr, pretty mode only.** Rule 3 has a test; a progress bar on stdout
  would break every agent reading JSON.
- **Never send a non-GET to production without asking** (rule 13). This entire phase is writes, so
  the rule applies to all of it and needs no new flag to say so: every live check goes to the
  sandbox, and the million-record test never leaves the process. The `--confirm` that guards
  updating one user guards updating 750 000 the same way.

## 7. Open questions

1. **`NEED-30` — `--records <file>` on the existing command, or a separate `braze bulk` verb?**
   §3.8 proposed the flag and the owner took it. The alternative reads more explicitly and isolates a surface that
   behaves very differently, at the cost of a second command tree and every one of the 95
   operations appearing twice — in `braze commands --json` and `docs/commands.md` included.
2. **`NEED-31` — what does `records.csv` do when a record has no identifier at all?** §33 says
   leave missing fields blank, but a row with no identifier and a `submitted` status is an audit
   entry nobody can act on.

`RISK-3` — how Braze attributes an error inside a 2xx — is **not** an open question for the owner.
It is a measurement, and Step 3 takes it.

## 8. Out of scope

`braze run resume <run-id>` (`BULK-11`, Phase 4) — but the audit format must already make
"submitted / failed / unknown / not started" answerable per source record, or resume becomes
impossible later. Worker threads: §38 rules them out for HTTP concurrency.
